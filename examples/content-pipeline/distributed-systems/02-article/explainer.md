# 从一个订单开始，理解分布式系统

点击下单，页面转了一会儿，显示请求超时。你再点一次，订单列表里却出现了两笔订单。

服务器到底有没有处理第一次请求？既然多部署几台机器是为了提高可靠性，为什么事情反而变复杂了？

我们从一个简单的订单系统开始，每次只增加一种机制，看看它解决了什么，又带来了什么问题。只需要知道：应用接收请求，数据库保存数据。

> 全文采用假设案例。订单编号、等待时间、日志和时序均为教学示意，不是实际测量结果或真实项目事故。

## 1. 一台机器忙不过来，先多开一个应用

最初，用户的请求由一个应用进程处理，订单保存在数据库里：

```text
用户 -> 应用 A -> 数据库
```

如果应用所在机器故障，用户就无法下单。如果瓶颈在应用的处理能力，可以部署另一个实例，让负载均衡器（load balancer）把请求分给它们：

```text
              -> 应用 A --+
用户 -> 负载均衡          +-> 数据库
              -> 应用 B --+
```

A 和 B 可以运行相同的代码。它们各自有内存、处理请求，并通过网络访问数据库。

多个独立计算节点通过网络通信，共同完成任务，这就是本文理解分布式系统（distributed system）的起点。节点通常是不同机器上的服务进程；一台电脑上也能用多个进程模拟节点。

如果最开始应用与数据库就部署在不同机器上，它们之间已经存在分布式边界。增加应用 B 是扩大了协作范围。

这里不需要先把系统拆成订单、支付、库存等微服务。微服务是一种服务划分方式；两个相同应用实例连接远程数据库，也有分布式问题。

多实例还暴露了一个差别：A 内存里保存的登录状态，B 不会自动知道。请求从 A 换到 B，用户可能被要求重新登录。可以把状态外置到共享存储，或者采用其他明确的状态管理方案，不能假设两份内存天然相通。

增加实例也不会让系统无限变快。如果瓶颈在数据库，A 和 B 可能只是一起等待数据库响应。数据库与负载均衡器的故障风险，也没有因多开一个应用而自动消失。

## 2. 请求超时了，订单却可能已经创建

可以暂时把应用实例想成订单登记柜台，把网络请求想成传话单：你递交申请，柜台登记，再发回回执。没有收到回执，无法直接判断柜台是否已经登记。

到这里类比不够用了，真实机制是：请求发送、服务端执行、响应返回，分别发生在不同阶段。客户端只能根据自己收到的信息判断。

假设客户端最多等待 2 秒。下面三种情况，在客户端看来都可能是超时：

| 远端实际发生了什么 | 客户端看到什么 |
|---|---|
| 请求没有到达应用 | 没有收到成功响应 |
| 请求到达了，应用还在处理 | 没有收到成功响应 |
| 订单已提交，响应没有及时返回 | 没有收到成功响应 |

第三种情况尤其容易被忽略：

```text
客户端                  应用 A                    数据库
   | -- 创建订单 --------> |                         |
   |                       | -- 保存订单 ----------> |
   |                       | <----- 提交成功 ------- |
   | <--- 成功响应未及时到达 |
   | 等待期限结束           |
```

客户端与服务端的示意日志可能分别是：

```text
客户端：request=r-001 result=timeout
服务端：request=r-001 order=O-100 result=committed
```

两条记录不矛盾。客户端记录的是观察，服务端记录的是执行结果。

超时意味着：在规定的等待时间内，没有获得所需响应。仅凭超时，无法断言操作失败，更无法保证远端已经停止执行。客户端不再等待，也不会自动撤销已提交的订单。[1]

这就是局部失败（partial failure）的一个例子：客户端到服务端的通信出了问题，服务端到数据库的工作却可能完成。系统没有一起成功，也没有一起失败。

## 3. 重试救回请求，也可能多创建一笔订单

如果第一次请求根本没送达，重试很有用。但如果第一次已经创建订单，第二次又被当作新购买，就会再创建一笔。

为了区分这两种意图，可以在用户发起一次购买时生成一个请求编号，重试时复用它：

```text
第一次购买尝试：user=U-1 request=r-001 -> 创建 O-100
同一意图的重试：user=U-1 request=r-001 -> 返回 O-100
用户又买了一次：user=U-1 request=r-002 -> 创建新订单
```

这种标识常叫幂等键（idempotency key）。幂等（idempotence）要求同一逻辑操作重复执行，不额外产生同类业务副作用。这里要避免的是重复订单；日志记录多了一行并不代表订单创建不幂等。[2]

同样商品、同样数量、同样收货地址，也可能是用户真的想买两次。因此不能仅靠参数相同就认定重复请求。

服务端还需要处理并发。下面的写法有漏洞：

```text
A 查询 r-001：没有记录
B 查询 r-001：没有记录
A 创建订单
B 创建订单
```

两次请求都能查到不存在。示例中的修法是：在数据库中给“用户标识 + 请求编号”建立唯一约束，并把幂等记录与订单创建放进同一个本地事务（local transaction）。其中一次提交成功后，重复请求依据已有记录取得订单结果。遇到并发中的未完成请求，还要明确返回处理中、等待或让客户端稍后查询，不能凭空返回成功。

为什么强调同一事务？如果先记下请求编号，创建订单之前进程就崩溃，后续请求可能被误判为已经成功；如果先创建订单，记录编号之前崩溃，又可能再次创建。[2]

这个方案只说明同一数据库事务内如何避免重复创建订单。它不能自动覆盖远程支付、库存服务等副作用。还要约定：同一编号带了不同参数怎么办、记录保存多久、过期后迟到的重试如何处理。

重试也需要限度。对适合重试的临时错误设置次数和总期限，逐渐拉开重试间隔，并加入随机扰动，避免大量客户端同时重试。参数错误不会因为多试几次就变正确；结果不明时，按同一业务编号查询状态也是一条恢复路径。

## 4. 多存一份数据，读出来却不一样

两个应用仍然依赖一个数据库。为了在数据库故障后恢复服务，或者分担部分查询，可以增加副本（replica），通过复制（replication）把变更传过去：

```text
写入 -> 数据库主节点 -- 复制变更 --> 数据库副本
                                   ^
                                   |
                                  查询
```

这里采用单主写入的教学模型，并非所有系统都采用这种结构。

采用异步复制时，主节点可以先提交订单并向调用方返回成功，再由副本接收、应用变更。于是会出现这条时序：

```text
t1：主节点提交 O-100，返回创建成功
t2：用户查询副本，结果为空
t3：副本应用变更，再次查询得到 O-100
```

订单没有被删除，查询碰到了复制延迟。如果主节点在变更复制出去之前永久故障，切换到副本还可能丢失这笔已确认写入。[3]

为了减少这类风险，可以让写入等待指定副本确认。但“确认”具体是什么意思，必须说清：副本收到数据、写入持久化存储、完成回放使查询可见，是不同阶段。PostgreSQL 的同步复制配置就区分了这些确认条件。[3]

所以，“用了同步复制”并不能推出“任意副本上的查询都能马上读到新订单”。未参与确认的副本可能落后；只完成持久化、还没回放的副本也可能尚未让查询看到变更。

读路径同样重要。写后查询主节点，在没有后续修改且采用适当读取语义的示例里，可以避开落后副本；但旧缓存、数据库快照、错误路由仍可能改变最终观察。

如果希望对外承诺更强的读写语义，就要定义一致性模型（consistency model）。其中，线性一致性（linearizability）可以这样理解：操作看起来在调用与返回之间的某一瞬间生效，而且尊重已经发生的先后关系。

假设 O-100 的创建已经返回成功，之后才发起订单查询，并且没有其他操作修改或删除它，满足这个承诺的查询不能返回不存在。若读写时间重叠，则还需要考虑它们允许的先后排序。[1]

副本可以在物理上短暂不同步，只要系统的协调和读路径没有让对外结果违反承诺。不能只看副本数量，就判断系统提供了哪种一致性。

## 5. 两边都活着，断网后却无法同时满足承诺

现在，主节点 A 和副本 B 都在运行，却无法互通。这叫网络分区（network partition）：节点被分成不能正常交换信息的几组。

```text
用户甲 -> A：创建 O-100 成功
          A --- 通信中断 --- B
                           ^
                           |
用户乙 --------------------+：查询 O-100
```

假设 A 在分区期间接受写入并确认成功，之后用户乙向 B 查询。B 没有收到订单变更。

B 面临一个无法靠本地数据解决的问题：A 是创建了 O-100，还是没有创建？对 B 来说，两种情况都可能表现为没有收到消息。

如果 B 按旧数据回答不存在，可能违反前面的线性一致性承诺。如果 B 等待通信恢复再确定答案，就无法保证在分区持续时完成这个请求。直接返回暂不可用虽然是一个网络响应，也没有成功完成用户请求的订单读取。

这就是 CAP 在这个例子里的矛盾。[4]

- C，Consistency：这里指线性一致性这类原子读写保证，不是 ACID 中的数据约束一致性，也不是“所有副本每一瞬间都相同”。
- A，Availability：所有发给非故障节点的合法请求最终得到符合操作语义的响应，不承诺固定毫秒内完成，也不等于日常说的服务可用率。给所有请求返回错误不能算满足它。
- P，Partition tolerance：讨论的系统需要面对节点之间可能无法通信的情况。

在允许网络分区的模型下，无法同时保证 C 和 A。把 CAP 背成三个任意选两个，很容易漏掉这条条件。

也可以让 A 在失去必要通信后停止确认新的写入。这样避免了上面的成功写入与旧读冲突，却牺牲了那些写请求的可用性。具体阻塞哪些操作，取决于协议和数据模型。

实际产品不必对所有功能采用同一策略。库存扣减需要守住防超卖的约束；商品介绍页可能允许展示旧版本。接受旧读之后，还要设计恢复通信后的同步和冲突处理，不能把“允许暂时不同”当成永久不管。

## 6. 找一个负责人，也要限制旧负责人继续写

单主结构看起来好理解：由一个负责人安排写入，其他副本跟随。问题是，负责人没回应时，它到底是坏了，还是只是与其他节点断开了？

如果另一侧选出新负责人，而旧负责人继续独立确认写入，两边可能形成不同历史。

共识（consensus）协议要约束节点怎样决定被接受的记录及其顺序。Raft、Paxos 等协议用于这一类协调；这里先不展开算法。

以采用 Raft 的 etcd 为例，在固定三个投票成员 A、B、C 的示意配置中，多数是两个。分区为 A、B 一组，C 单独一组时，两个分区不能同时各有多数。[5]

```text
多数侧：A + B   |   隔离侧：C
       2 票     |          1 票
```

在协议与成员配置正确的前提下，失去多数的节点即使还活着、甚至暂时认为自己是负责人，也不能独立完成依赖多数确认的新提交。多数侧要能恢复推进，还需要满足选举、节点健康和通信等条件，不代表断网后立刻无延迟切换。

“多数同意”本身远远不够。协议还要处理负责人更替、旧记录保留和操作顺序，不能随便给每次写入投票就宣称实现了共识。

共识也不会判断业务是否写对了：如果大家一致提交了一条错误的库存变更，业务照样错。它更不能自动让系统里的缓存、消息队列和外部支付一起成为一个事务。

## 7. 一笔业务拆成两个服务，事务也被拆开

到目前为止，我们讨论的是订单写入与它的副本。再把库存管理拆成独立服务，一次下单就要跨越两个存储边界：

```text
订单服务 -> 订单数据库
    |
    +---- 请求预留库存 ----> 库存服务 -> 库存数据库
```

即使每个服务内部都正确使用本地事务，也可能出现：订单记录提交成功，库存预留失败。交换执行顺序，则可能库存预留成功，订单记录保存失败。

订单数据库中的事务不能自动撤销库存数据库已经提交的操作。远程调用超时还会重新带来第 2 节的问题：库存可能已经预留，只是结果没有传回来。

一种容易理解的处理方式，是把订单先保存为待确认，让它通过持久化状态转换记录进度：

```text
待确认 -> 库存预留成功 -> 已确认
待确认 -> 明确无法预留 -> 已取消
```

结果未知时先查询或受控重试，不能把超时直接当作库存不足。如果后续明确需要取消，可能还要释放已经预留的库存。这叫补偿（compensation）：执行新的业务动作，抵消之前动作的影响。

补偿不是时间倒流。库存释放本身可以失败，也可能收到重复请求，所以它也需要幂等、状态记录和恢复机制。发出去的通知无法从用户记忆里撤回，已经完成的支付退款也有自己的流程和约束。

通过消息驱动这类流程时，还存在一个间隙：订单事务已经提交，进程却在发消息之前崩溃，后续库存流程就可能没有被触发。事务内保存待发送事件、再可靠投递，是解决这一间隙的一类办法；仅仅接入 MQ 不会自动消除它。

最终一致性（eventual consistency）通常意味着：停止新的更新后，在通信恢复、更新能够传播、冲突得到处理等前提下，副本最终收敛。它没有单靠名字就承诺多久收敛。[4]

在订单流程中，类似的恢复承诺需要具体机制支撑：待处理记录不能因进程重启丢失，失败任务要能再执行，重复操作不能多扣库存，无法自动完成的情况要进入可追踪的异常状态。跨服务业务完成与副本收敛是相关但不同的问题，不要统称为“等一会儿就好了”。

这只是理解一种设计方向。业务还可能需要更强的跨存储原子性保证，采用协调提交等方案，同时承担对应的等待和故障处理成本。本文不提供可直接上线的下单实现。

## 回到第一次下单超时

现在再看页面上的超时，我们有了更具体的问题：服务端是否创建了订单？重试是否复用购买申请编号？查询是否读到落后副本？库存是否还在等待确认？恢复任务有没有持续推进？

分布式系统首先让我们面对这些事实：节点各有自己的状态，通信需要时间，故障可以只发生在一部分，调用方的信息也可能不足以确定结果。增加机器以后，数据如何传播、操作何时确认、失败如何恢复，都需要明确设计。

本文没有覆盖分片、全局时间、完整共识算法和分布式事务实现。先用下面的问题检查自己能否解释已有模型，再继续深入。

1. 为什么客户端超时，服务端日志却能显示订单已经提交？
2. 为什么幂等键要区分购买意图，而不能只对商品参数取哈希？
3. 为什么有副本、甚至有同步复制，也不代表任意读取都是最新的？
4. 两个不能通信的节点，为什么无法同时承诺所有请求成功与线性一致性？
5. 为什么订单服务和库存服务各自有事务，整笔下单仍然可能只完成一半？
