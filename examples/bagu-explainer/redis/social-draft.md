## 第 1 页：Redis 为什么这么快

**后端八股总结 · Redis 篇**

**① Redis 为什么这么快**

**1. 纯内存操作**：Redis 的数据全部存放在内存中，读写都在内存里完成，不经过磁盘，这是它快的根本原因，单机轻松 10w+ QPS。

**2. 单线程模型**：Redis 的命令执行采用单线程，没有锁竞争、没有线程上下文切换的开销，也不用考虑并发安全问题。

**3. IO 多路复用**：Redis 采用 epoll 实现IO多路复用，一个线程就能监听成千上万个客户端连接，哪个连接有数据就处理哪个，不需要为每个连接单独开线程。

**4. 高效的数据结构**：底层针对不同场景深度优化，比如 SDS 动态字符串、跳表、压缩列表、支持渐进式 rehash 的哈希表。

加分点：Redis 6.0 引入了多线程，但只用来处理网络 IO 的读写和协议解析，命令执行仍然是单线程，别答成"Redis 6.0 变成多线程了"。

## 第 2 页：数据类型与应用场景

**② 数据类型与应用场景**

**String 字符串**：最常用。缓存 JSON 对象、计数器（incr 原子自增，做限流/点赞数）、分布式锁（set nx ex）。

**Hash 哈希**：存对象，字段可以单独读写。典型场景是购物车：用户 id 为 key，商品 id 为 field，数量为 value。

**List 列表**：双向链表，两头进出都快。做最新列表（动态、朋友圈时间线）、简单的消息队列（lpop / brpop 阻塞消费）。

**Set 集合**：自动去重。抽奖（spop 随机弹出）、共同关注（sinter 交集）、标签推荐。

**ZSet 有序集合**：带分数排序的集合。排行榜（zincrby 加分、zrevrange 取前 N）、延时队列（分数存到期时间，轮询取到期任务）。

加分类型：BitMap 位图（签到打卡、活跃用户）、HyperLogLog（亿级 UV 统计，0.9% 误差换 12KB 内存）、GEO（附近的人）、Stream（专业消息队列）。

## 第 3 页：缓存穿透、击穿、雪崩

**③ 缓存三兄弟：穿透 · 击穿 · 雪崩**

**缓存穿透**：查询的数据在缓存和数据库里都不存在，缓存永远不可能命中，每次请求都打到数据库，相当于缓存被"穿透"了。常见于恶意请求不存在的 id。
解决：① 布隆过滤器，把存在的 key 提前放进去，不存在的直接拦掉；② 把空结果也缓存起来，设一个较短的过期时间（如 60s）。

**缓存击穿**：某个热点 key 过期的一瞬间，大量并发同时查这条数据，全部打到数据库，把库打挂。
解决：① 互斥锁，只允许一个线程去数据库查并回写缓存，其他线程等待；② 热点数据设置逻辑过期/永不过期，由异步线程更新。

**缓存雪崩**：大量 key 在同一时刻集体过期，或者 Redis 宕机，请求洪峰全部压到数据库，引发连锁崩溃。
解决：① 过期时间加一个随机值，把过期时间打散；② 搭建主从+哨兵或集群保证 Redis 高可用；③ 服务端限流、熔断、降级保住数据库。

一句话区分：穿透是查"没有的数据"，击穿是"一个热点"倒了，雪崩是"一大片"全倒。

## 第 4 页：持久化 RDB 与 AOF

**④ 持久化：RDB 与 AOF**

**RDB 快照**：把某一时刻的内存数据以二进制形式整体写入 dump.rdb 文件。有 save（阻塞主线程）和 bgsave（fork 子进程写，主流）两种触发方式。优点：文件紧凑、恢复速度快；缺点：两次快照之间的数据会丢，宕机时丢得多。

**AOF 日志**：把每条写命令追加到 aof 文件，先执行命令再记日志。刷盘策略三种：always 每条命令都刷盘（最多丢 1 条）、everysec 每秒刷一次（默认，推荐）、no 交给操作系统（性能最好，丢得最多）。优点：丢数据少；缺点：文件大、恢复慢。

**AOF 重写**：日志越写越大，bgrewriteaof 会 fork 子进程，根据当前内存数据生成一份等价的最小命令集，解决文件膨胀问题。

**混合持久化（4.0+，重点）**：重写时先写一份 RDB 全量数据，再追加之后的增量命令。恢复快 + 丢得少，两头兼顾，现在是生产推荐配置。

## 第 5 页：过期删除与内存淘汰

**⑤ 过期删除与内存淘汰**

**过期删除策略**：Redis 对带过期时间的 key 采用"惰性删除 + 定期删除"组合。惰性删除：访问 key 时检查，过期就删；定期删除：默认每 100ms 随机抽取 20 个带过期时间的 key，删掉其中过期的，如果过期比例超过 25%，继续抽，直到比例降下来或达到时间上限。

**内存淘汰策略（8 种）**：内存达到 maxmemory 之后触发。重点记四个：noeviction（默认，不淘汰，写入直接报错）、allkeys-lru（全库淘汰最近最少使用的 key，缓存场景最常用）、volatile-lru（只在设置了过期时间的 key 里淘汰）、allkeys-lfu（4.0 新增，淘汰访问频率最低的，适合有突发冷访问的场景）。

**高频追问：Redis 和 MySQL（InnoDB）的 LRU 有什么区别？**
Redis 是近似 LRU：不维护全局链表，随机采样若干 key（默认 5 个），淘汰其中最久未使用的，省内存。
InnoDB 是严格的 LRU 链表，并且做了改进：分成 new/old 两区，还在头插，防止预读和全表扫描把热点页冲掉。

## 第 6 页：高可用：主从 · 哨兵 · 集群

**⑥ 高可用：主从 · 哨兵 · 集群**

**主从复制**：一主多从，读写分离。从库执行 replicaof 之后先全量同步：主库 bgsave 生成 RDB 发给从库，之后把期间的新写命令持续发给从库增量同步（基于 repl_backlog 环形缓冲区，断连太久缓冲被覆盖就要重新全量）。缺点：主库挂了需要人工切换。

**哨兵 Sentinel**：解决主库挂了没人管的问题。哨兵集群持续心跳检测，一个哨兵 ping 不通主库算"主观下线"，超过 quorum 个哨兵都认为挂了才算"客观下线"，然后自动选举新主库（依次比较优先级、复制偏移量、runid 最小），最后通知客户端切换。哨兵之间也要互相选举出 leader 来执行故障转移（Raft 思想）。

**分片集群 Cluster**：数据量单机放不下时，把 16384 个哈希槽分给多个主节点，key 通过 CRC16(key) mod 16383 算出槽位，定位到节点；每个主节点还可以挂从节点防单点。节点之间通过 gossip 协议通信，客户端可以连任意节点，key 不在当前节点会收到 moved 重定向。
