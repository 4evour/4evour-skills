## 第 2 页｜它解决的不是“Agent 记不住”

标题：

**问题已经从“记住”变成了“复用”**

正文：

普通 Memory 关心的是：怎样保存历史对话，并在下一次交流时找到相关内容。

但当多个 Agent 和成员共同工作时，问题会变成：一次成功的排障流程能否交给下一个 Agent？业务文档和代码关系应该怎样使用？哪些经验可以共享，哪些只能属于个人？

TencentDB Agent Memory 的回答，是把 Memory 从个人上下文扩展为一套团队经验资产系统。

核心大字：

**从“找回内容”走向“管理并交付经验”**

视觉中心：左侧“个人聊天记忆”，右侧“团队经验控制面”，展示问题边界的变化。

---

## 第 3 页｜四类资产

标题：

**四类资产，不是四个菜单**

四个模块：

**Chat Memory**
保存原始对话、事实、场景与长期认知，回答“这个人是谁，过去发生过什么”。

**Skill**
沉淀带版本和资源的工作方法，回答“同类任务下一次应该怎样做”。

**Wiki**
组织业务文档与概念关系，回答“团队已经知道什么”。

**CodeGraph**
保存文件、符号与调用关系，回答“代码怎样连接，修改会影响哪里”。

页底结论：

**它们共享 Owner、版本、权限和装配关系，但没有被强行压成同一种文本块。**

强调句：

**异构经验可以共享治理，不必共享同一种数据结构。**

视觉中心：四种资产以不同形态进入同一个治理层，下方仍连接各自的数据结构。

---

## 第 4 页｜L0–L3 分层记忆

标题：

**分层的价值，不只是把摘要越写越短**

层级文案：

**L0 Conversation｜原始证据**
保留对话原文、时间和完整上下文。

**L1 Atom｜可检索事实**
提取偏好、约束、事件与决策。

**L2 Scenario｜场景知识**
恢复项目、任务或长期活动的上下文。

**L3 Persona / Core｜稳定认知**
帮助 Agent 快速进入用户和团队语境。

页底结论：

L1–L3 都可能受到模型提炼误差影响，因此系统仍保留 L0。上层负责高效使用，下层负责核验、追溯与重新加工。

强调句：

**模型生成的认知应该可以重算，原始证据不能消失。**

视觉中心：L0 到 L3 的分层剖面；向上越来越抽象，向下可以回到证据。

---

## 第 5 页｜经验如何进入 Agent

标题：

**Push 概览，Pull 证据**

左侧：

**Push｜主动装配**

- L2/L3 提供相对稳定的背景
- L1 根据当前问题动态召回
- 设置超时、数量和字符预算

右侧：

**Pull｜按需展开**

- 需要核对时再搜索原始对话
- 需要文档时调用 Wiki 工具
- 需要代码关系时查询 CodeGraph

中部结论：

它没有把所有记忆、文档和代码一次塞进 Prompt，而是先提供低成本概览，再让 Agent 在需要时逐步取回证据。

强调句：

**Memory 的目标不是召回得最多，而是提高每个 Token 的决策价值。**

视觉中心：左侧经验中心向 Agent 推送轻量概览，Agent 再向下钻取原始对话、Wiki 和 CodeGraph。

## 第 6 页｜项目判断与竞品坐标

标题：

**它不是更强的记忆算法，而是更重的经验平台**

竞品坐标：

**Mem0**
更接近轻量、通用的 Agent Memory Layer。

**Graphiti**
更专注事实有效期、来源和时序关系。

**Letta**
更强调与有状态 Agent 运行时的深度结合。

**TencentDB Agent Memory**
把 Chat Memory、Skill、Wiki 和 CodeGraph 放进统一的 Owner、版本、权限、绑定和交付闭环。

适用判断：

适合多个 Agent 或团队成员共享长期经验，并且在意权限、版本和定向装配的场景；如果只是单个 Bot 保存少量用户偏好，这套架构很可能过重。

边界小字：

自动资产路由仍在迭代；公开 Benchmark 尚未由本文独立复现；生产规模下的成本、延迟与隔离能力仍需实际验证。

收束句：

**它最值得带走的，不是“记住更多”，而是让正确的经验，以正确的形态，被正确的 Agent 复用。**

视觉中心：四个项目按“主抽象”并列定位，避免使用简单的胜负打分榜。

## 三、发布正文

最近完整读了一遍 TencentDB Agent Memory 的 README 和关键源码。

如果只看名字，它很容易被理解成又一个“给 Agent 增加长期记忆”的项目：保存聊天记录、提取用户偏好，再通过向量检索放回上下文。

但我的理解是，它真正有辨识度的地方并不是某个新的检索算法，而是把 Agent 工作中产生的经验拆成了四类资产：Chat Memory、Skill、Wiki 和 CodeGraph。

这四类经验没有被强行存成同一种文本块。它们保留各自的数据结构和消费方式，同时在上层共享 Owner、版本、权限、可见性和 Agent 绑定关系。换句话说，项目开始处理的已经不只是“模型怎样记住”，而是“团队经验怎样被治理和交付”。

其中我认为最值得研究的还有两点：

第一，L0–L3 并不是简单的多级摘要。上层的场景和画像由模型提炼，下层仍保留原始对话，让模型生成的认知可以被核验和重新计算。

第二，它采用了可以概括为“Push 概览，Pull 证据”的上下文策略。稳定背景和动态事实按预算进入上下文，原始对话、Wiki 和代码关系则在真正需要时通过工具继续展开。

这套设计更适合多个 Agent 或团队成员共享工作经验，也意味着它比普通 Memory SDK 更重。对于只需要保存少量用户偏好的单 Bot，轻量方案可能更直接；而自动资产路由、公开评测的可复现性和生产规模下的表现，也仍然需要继续验证。

这组 6 页图文先建立项目的核心认知。后续长文会继续展开源码路径、Skill 版本化、权限模型、Proxy 的失败回退，以及它与 Mem0、Graphiti、Letta 的具体差异。
