# 写作工作流（从零写内容时用）

解决两个问题：AI 味的解药必须在现场采集；文章永远赶不上项目进度。

## 一、PROJECT_LOG 协议

在每个项目仓库根目录放一个 `PROJECT_LOG.md`，规则极简：

```markdown
## 2026-08-19
- 把 RAG 检索从 BM25 换成了混合检索，纯 BM25 在官方资料长文本上召回差（耗时 3h，
  第一版想用向量库，放弃了：本地起 Docker 太重）
```

- 只在当下记，每条 ≤3 行，随手写完就走
- **专记"当时的混乱"**：第一版是什么、为什么放弃、卡了多久、什么感受
- 数字（耗时、次数、内存、命中率）当场记，事后回忆只会编
- 这个 log 同时是面试 STAR 故事的素材库——每条"失败→原因→修复"就是一道现成的行为面试题

没有 log 的旧项目：改稿时把缺的细节做成坑位清单还给作者，一轮问清，不猜。

## 二、合成内容（三平台）

所有内容 = 从 log 里挑主题合成，不靠回忆。先过素材门，再按平台合成：

1. 从 log 挑出同一主题的 5-10 条记录，按时间排
2. 过素材门：每计划的小节，指出它用的具体素材（哪条 log、哪个数字）。指不出的砍掉
3. 找事故现场：log 里最像"故事"的那条（有失败、有转折），放正文中间当锚点
4. 按平台合成：

**博客**：为什么做 → 第一版怎么错的 → 怎么发现 → 修法 → 代价和残留问题。1500 字上下的复盘文，素材够了半天写完。

**B站稿**：先列讲述顺序（钩子 30 秒 → 问题 → 踩坑过程 → 解法 → 代价和局限），再展开成逐字稿，每段念出来 5-15 秒。形态细节见 platforms.md「B站口语稿」。

**小红书**：只抽一个最锋利的点——一个坑、一个数字对比、一个反直觉结论。300-800 字，开头两行直接抛结论。一条 log 通常就是一条笔记。

5. 改稿走 SKILL.md 的执行顺序 + patterns.md，平台语体对照 platforms.md

## 三、坑位协议

写作中遇到"这里需要一个真实细节但素材里没有"时：

- 插入 `[填：具体问题]`，如 `[填：当时是什么让你决定加这个检查]`
- 集中列在文末还给作者，一轮问清
- **宁可留洞，不许编故事**。编出来的"我卡了三天"面试被追问一句就穿帮，比没有还糟

## 四、过时处理

文章落后于项目进度是常态，不返工旧文：

- 旧文顶部加一行：`> 2026-XX-XX 更新：后续变化见《新文章标题》`
- 新变化写新文，系列链接串起来
- 只有旧文出现**事实错误**（接口名变了、架构描述已不成立）才回去改，且在文首注明改过什么

## 五、交付前自检

1. 跑 `scripts/deslop_check.py`，逐条核对命中（自然语境的命中可放过）
2. 全文搜「不是……而是……」→ 保留 ≤1 处
3. 每个小节结尾：有"这说明/这展示了"→ 删
4. 引号里的抽象名词 → 换具体所指或删
5. 连续 ≥5 的碎句清单 → 关键项补"为什么/代价/坑"
6. 全文 ≥2 处真实的时间/失败/情绪
7. 假揭示（"看似 X 本质 Y / 真正的关键"）→ 删壳，落到具体事实
8. 模糊归因（"业内人士/研究表明"）→ 点名真实来源或删
9. **信息账本回扫**：数字、专名、版本号、限定词，与原素材逐项对，没丢没变没升级
10. 朗读一遍：任何一句"换个博主也成立"→ 重写或删
11. B站稿加一项：念全文，需要回听两遍才懂的句子 → 重写
