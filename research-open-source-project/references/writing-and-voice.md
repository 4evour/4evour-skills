# 技术文章与写作语气标准

## 默认作者人设

以已经替读者完成初步调研的工程师同行身份写作。保持好奇、具体、克制；证据充分时明确给出判断。

不要像居高临下的老师、厂商、咨询报告或新闻聚合账号。

若项目根目录存在 `VOICE.md`，在不违背事实完整性的前提下遵循它；否则创建包含目标读者、内容承诺、语气、禁止表达和固定栏目的草稿。

## 结构约定

1. **问题**：陈述具体工程问题，而不是泛泛的行业趋势。
2. **核心洞察**：在全文前三分之一给出中心论点。
3. **证据与机制**：解释代码路径、数据模型、失败行为和替代方案。
4. **设计权衡**：把每项代价放在导致它的收益旁边。
5. **行动判断**：说明谁适合使用，以及读者可以迁移什么原则。

标题必须承载论点。优先写“为什么经过 LLM 提取后仍要保留原始证据”，而不是“技术实现”。

## 语气规则

- 先给出发现，再说明它如何得到。
- 使用第一人称表达解释：“我的理解是……”“我会把它放在……层”。
- 对已验证行为使用直接语气：“流水线在远程提取前先记录 L0。”
- 明确写出文件、符号、测量结果或官方来源。
- 第一次出现非常用术语时，用通俗语言解释。
- 只有真正并列的内容才使用列表。
- 使用短段落，但不要把文章切成互不相连的卡片。
- 精确表达不确定性：“现有基准尚未证明”，而不是“可能吧”。

## 禁止模式

- 没有检查论证需要就机械复制 README 章节顺序。
- 空洞钩子：“终于有人讲清楚”“一分钟看懂”“建议收藏”。
- 无依据的最高级：“最强”“全面领先”“革命性”。
- 套话式 AI 表达：“值得注意的是”“在当今快速发展的时代”，或反复使用“不仅……更……”。
- 没有机制的膨胀抽象：“重塑范式”“重新定义未来”。
- 只重复开头、不增加决策判断的结论。

## 原创分析要求

每个主要分析章节至少包含一项：

- README 中没有的代码观察；
- 跨多个组件的综合判断；
- 明确的设计权衡；
- 反方观点或失败模式；
- 能澄清系统位置的竞品比较；
- 可复用的工程原则。

交付前执行这项检查：

> 如果读者已经读过 README，这一节还能增加什么新理解？

必要的项目背景章节可以准确复用官方解释，但必须注明来源并保持简洁。没有增加 README 之外理解的分析章节需要重写。

## 论断表达

### FACT

“`auto-recall.ts` 并行执行关键词与 Embedding 检索，然后使用 RRF 合并排序结果。”

### INFERENCE

“我的理解是，真正的差异不在 RRF 本身，而在检索之外更完整的资产交付闭环。”

### OPINION

“对于只保存少量偏好的单 Bot，这套架构可能比实际需要更重。”

### OPEN

“现有公开材料还没有说明，长期存在的矛盾事实会如何解决冲突。”

## 平台适配

始终把 `article.md` 作为母稿，再派生平台格式：

- 小红书：交付一个压缩但完整的认知模型；不要把每段正文都变成卡片，也不要用名词列表代替解释。
- PDF：使用图片、图注和来源形成连续阅读体验；仅在 Markdown 批准后导出。
- 博客：保留代码路径、来源链接和论断边界。

面向专业技术分享时，删除没有证据的“爆火”“新星”等热度描述和模板化钩子。让卡片解释机制，让发布正文补充来源、判断、限制和阅读引导。
