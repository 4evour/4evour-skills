# 视觉证据工作流

## 原则

使用图片解释关系或证明产品真实状态。不要把图片当作装饰，也不要用图片替代缺失的分析。

## 来源选择

同时考虑证据强度和目标格式可读性：

1. 在目标尺寸下可读时，使用仓库原生架构图和真实界面资源。
2. 需要精确表达时，使用聚焦后的代码片段、表格或实测图表。
3. 官方资源过宽、过密或不适合目标平台时，制作可追溯的作者重绘图。
4. 关系仍难以解释时，使用生成式知识卡片。

不要把横向官方图强行塞入 3:4 卡片。重绘时记录 `redrawn_from`，并让图中论断可追溯到官方资源、代码或论断账本。

## 视觉方案结构

创建：

```markdown
# 视觉方案

| ID | 目的 | Claim IDs | 来源类型 | 来源/路径 | 处理方式 | 状态 |
|---|---|---|---|---|---|---|
| V-01 | 解释数据流 | C-003,C-004 | 官方 | assets/flow.png | 复用并添加图注 | 已批准 |
```

针对每张图回答：

- 它回答什么问题？
- 它支持论断账本中的哪些记录？
- 它属于官方证据、代码推导图还是解释性插图？
- 删除它会损失什么信息？
- 它是否包含必须保持准确的文字？

## 复用仓库图片

- 解析 README 图片链接，优先使用原始文件，而不是浏览器截图。
- 验证资源存在于被调研分支或提交上。
- 只裁切浏览器边框或空白边距，不修改产品内容。
- 添加图注，说明图片证明了什么，并标记其为官方图片。
- 不把界面截图当作正确性、性能或成熟度的证据。

## 创建关系图

仅在需要表达独立综合判断时制作原创关系图，例如：

- 控制平面与数据平面；
- 原始证据 → 派生记忆 → 交付 → 反馈；
- 按系统层级定位竞品；
- 收益 → 机制 → 代价；
- 跨越多个包的代码路径。

把作者图标记为分析图，不要标记为官方架构。

## 使用 baoyu-xhs-images

当用户需要小红书卡片，或少量知识图能明显改善文章时，使用 `baoyu-xhs-images`。

调用前：

1. 批准 `article.md` 和 `visual-plan.md`。
2. 制作社交图文时，在内部批准 `channel-strategy.md` 和 `card-script.md`。
3. 只选择视觉方案中状态为 `generated` 的项目。
4. 提供中心论点、卡片精确文字、Claim ID、禁止添加内容和官方参考图。
5. 用户没有指定时，专业技术讲解优先选择 `sketch-notes` 或 `notion`。
6. 大多数技术卡片只讲一个关系，并包含 3～5 个支撑点。

随后完整遵循 `baoyu-xhs-images` Skill，包括：

- 加载其 `EXTEND.md`；
- 在 `reviewed` 模式确认策略、风格、布局、配色和数量；在明确的 `one-pass` 模式使用已批准的 `channel-strategy.md` 默认值；
- 生图前写好独立提示词文件；
- 先生成第 1 张，并将其作为后续图片的视觉锚点；
- 覆盖提示词和图片前创建备份；
- 文字错误时重新生成，不在图片上涂改。

生成后检查真实尺寸，并执行 `social-card-quality-gates.md`。提示词要求某个宽高比，不代表输出文件真的符合。

不要在本 Skill 中复制生图实现。

## 长文图文平衡

插图文章或 PDF 应保持连续阅读体验：

- 文字承载论证；
- 关系图承载结构；
- 截图承载产品证据；
- 表格承载精确比较；
- 生成式卡片只承载便于记忆的总结。

不要把每一页都做成独立卡片；每个主要章节最多放一张高密度生成式卡片。
