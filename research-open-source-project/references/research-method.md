## 1. 证据来源层级

针对每个论断，按以下顺序选择证据：

1. 实际执行行为、测试与测量结果。
2. 被调研提交上的源代码。
3. 官方技术文档、更新日志和 README，用于证明已记录行为与项目意图。
4. 官方产品图和截图。
5. 维护者的 Issue、PR 和讨论。
6. 独立研究或评测。
7. 社区评论仅作为个案背景。

把 README 当作一手资料：它可以证明项目声明的意图、公开接口、术语、文档流程和自报结果，但不能单独证明运行时正确性、相对优势、生产成熟度或基准可复现性。截图可以证明界面存在，不能证明功能正确、快速或已达到生产水平。

创建 README 复用表，为每项材料选择一种处理方式：

- `reuse`：注明来源后保留准确的定义、表格、图或简明解释；
- `adapt`：围绕文章论点重新组织有用的官方材料；
- `verify`：用代码或其他来源核验行为、性能、成熟度或比较结论；
- `exclude`：排除宣传性、过时、重复或无关内容。

## 2. 仓库分析顺序

### 第一遍：建立系统地图

记录语言、包、服务、入口、存储系统、外部依赖、协议、构建工具和部署单元。

### 第二遍：追踪价值路径

至少追踪一条跨越以下阶段的路径：

`输入 → 校验 → 转换 → 持久化 → 检索 → 交付 → 反馈`

记录具体文件和关键函数，同时标记异步边界、队列、缓存、重试、超时、锁和失败行为。

### 第三遍：检查工程证据

检查测试、CI、Linter、迁移、可观测性、错误处理、基准、部署文档和已知限制。若架构看起来很强但验证薄弱，必须如实表达。

### 第四遍：主动寻找反证

搜索 `TODO`、`FIXME`、`unsupported`、`limitation`、`roadmap`、`fallback`、`retry`、`timeout`、`mutex`、`queue`、`experimental`、`beta`、`private repository` 和基准限制。寻找与最简单产品叙事相冲突的代码。

## 3. 证据地图结构

为了让校验脚本工作，严格使用以下标题：

```markdown
# 证据地图

## 源码状态
## README 复用表
## 官方主张
## 架构
## 代码证据
## 工程证据
## 限制
## 矛盾
## 开放问题
```

代码证据使用以下格式：

```markdown
### EV-001 — 简短发现
- 路径：`path/to/file.ts`
- 符号：`functionOrClass`
- 观察：代码实际做了什么。
- 含义：为什么重要。
- 其他解释：还可能如何解释。
- 置信度：high | medium | low
```

## 4. 独立洞察检查

中心论点必须通过以下检查：

- **增量价值检查**：已经读过 README 的读者，是否还能获得新的因果解释、工程后果、边界、比较或决策依据？
- **决策价值检查**：它是否改变工程决策或认知模型？
- **反方观点检查**：能否公平陈述一个有力的其他解释？
- **边界检查**：是否明确论点在哪些条件下不成立？
- **创新位置检查**：创新究竟位于算法、数据模型、系统边界、工作流、治理还是产品封装？
- **证据多样性检查**：支撑是否来自不止一种证据？

任何一项回答为“否”时，继续研究，不要用包装掩盖摘要缺乏洞察的问题。

## 5. 竞品比较方法

按稳定维度比较：

| 维度 | 问题 |
|---|---|
| 核心抽象 | 产品把什么对象视为中心？ |
| 数据模型 | 记录、向量、图、文件、块、工具，还是多类资产？ |
| 更新方式 | 同步、后台、增量、版本化还是时序化？ |
| 检索/交付 | 搜索、注入、常驻状态还是工具调用？ |
| 治理 | 所有权、ACL、版本、租户和装载配置如何处理？ |
| 耦合方式 | SDK、服务、Agent Runtime、框架插件还是代理层？ |
| 验证证据 | 测试、基准、来源追踪和公开评测如何？ |
| 运维成本 | 需要哪些服务、数据库、队列、模型调用和故障面？ |

不要把 Star 数量当作核心技术论据。对会变化的事实记录访问日期和来源 URL。

## 6. 工程风险问题

即使文档没有提到，也要主动追问：

- 提取或索引执行到一半失败时会怎样？
- 大任务是否会阻塞小任务？
- 派生数据能否从原始证据重新计算？
- 冲突、失效和时间如何处理？
- 哪个组件会成为扩展性或可用性瓶颈？
- 增强层失败时能否放行，避免阻塞主链路？
- 权限是否同时在查询时和检索后执行？
- 成本能否归因到用户、租户、资产和请求？
- 基准是否真正测量了项目声称的价值，能否复现？
